CVE-2026-63030 & CVE-2026-60137 (wp2shell) — Vulnerability Advisory

Audience: Vuln Management / SOC / IR / Detection Engineering / IT Ops  ·  July 21, 2026
Executive Summary

CVE-2026-63030 and CVE-2026-60137 are two WordPress Core vulnerabilities that chain together into an unauthenticated remote code execution path, tracked publicly as “wp2shell.” An unauthenticated attacker targeting a default WordPress installation on versions 6.9.0–6.9.4 or 7.0.0–7.0.1 can create an administrator account and execute arbitrary code with no plugin, theme, or credential requirement.[3][8]

Cardinal Trust Financial operates a public-facing WordPress site that falls within the affected version range and is directly exposed. Patch to WordPress 6.9.5 or 7.0.2 immediately and audit for post-exploitation artifacts before restoring trust in the environment.[3][10]

Both CVEs are actively exploited, require no authentication, affect a default installation, and have weaponized public exploits available. WordPress 6.8.x is not vulnerable to the full RCE chain but remains exposed to the SQL injection component and must still be patched.[3]

Technical Details
Attack vector and exploitation mechanism

The chain begins at the WordPress REST API batch endpoint (/wp-json/batch/v1 or /?rest_route=/batch/v1), which accepts multiple sub-requests in a single HTTP call.[8]

CVE-2026-63030 — REST API route confusion. The batch handler maintains parallel arrays for parsed requests, route-handler matches, and validation results. When a member request fails to parse and returns a WP_Error, the code appends to the validation array but not to the matches array. The resulting index misalignment makes every subsequent valid request execute against the handler tuple of the next request, bypassing permission and schema checks.[8]

CVE-2026-60137 — SQL injection via author__not_in. Route confusion delivers an unvalidated request to the posts REST handler, where author_exclude maps to the WP_Query variable author__not_in. With schema validation bypassed, the value arrives as an attacker-controlled scalar string; WP_Query only sanitizes it when it is already an array, so a raw string is interpolated directly into the SQL WHERE clause.[8]

Escalation to RCE

SQL injection alone does not yield code execution. The chain proceeds through several additional steps:

  1. The SQL injection controls which rows WP_Query returns and caches as WP_Post objects; attacker-chosen field values land in the request-local object cache.
  2. The oEmbed cache write path reads from get_post(), now returning poisoned objects, and writes those fields back to the database as a legitimate post save.
  3. The poisoned fields create a forbidden parent loop; the loop-repair routine re-saves the posts nested, keeping a temporary administrator identity active across the nested save.
  4. A Customizer changeset save briefly switches the current user to an attacker-chosen administrator.
  5. A second poisoned post triggers the REST loader during that window by joining its status and type into the string parse_request.
  6. The nested REST request — originally rejected with 401 — re-executes as the administrator and returns 201, registering an attacker-controlled admin account, which is then used to upload a malicious plugin and execute arbitrary PHP.[8]

Interim mitigations

Patching is the only complete fix. Where patching cannot happen immediately, block anonymous access to /wp-json/batch/v1 and /?rest_route=/batch/v1 at the WAF layer, or install a plugin that disables anonymous REST API access entirely.[10] Wordfence Premium, Care and Response customers received a firewall rule on July 17, 2026; Free customers are scheduled for August 16, 2026.[3]

Impact Assessment

Cardinal Trust Financial's public WordPress site is an internet-facing asset running the usual plugin and theme ecosystem with a wp-admin panel and CRM/form integrations. It falls within the affected version range and is directly reachable from the public internet.

Successful exploitation grants administrator-level access to the site and arbitrary code execution at web server process privileges. Wiz Research observed the following post-exploitation activity against cloud-hosted WordPress instances within hours of disclosure:[1]

  • Malicious plugin uploads (/wp-admin/update.php?action=upload-plugin) installing persistent backdoors.
  • User enumeration via /wp-json/wp/v2/users?context=edit, harvesting admin usernames and email addresses.
  • LFI attempts via admin-ajax.php?template=../../../wp-config, targeting database credentials and auth keys.
  • Successful authenticated sessions to /wp-admin/ (HTTP 200 responses confirmed).

CRM and lead-capture integrations mean credentials or API keys stored in wp-config.php are accessible to an attacker achieving LFI or RCE. WordPress is not directly connected to core banking or payment rails, but a persistent foothold on the WordPress server is a viable staging point for reconnaissance against adjacent AWS infrastructure.[1][2] Lateral movement and data exfiltration were unconfirmed as of July 21, 2026; monitoring is ongoing.

Verification steps — confirming remediation
  1. Run wp core version and confirm output is 6.8.6, 6.9.5, or 7.0.2.
  2. Cross-check against the public checker at wp2shell.com.
  3. Confirm the WAF rule is active by sending a test POST to /wp-json/batch/v1 and verifying it is blocked.
  4. Review Wordfence firewall logs for blocked requests to the batch endpoint as a secondary signal.
  5. Re-run wp core verify-checksums after patching to confirm no Core files were modified during any exploitation window.
